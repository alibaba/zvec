## 2. 环境与方法

- Apple M3 Pro，11 核，36 GiB；macOS 26.6.2；AppleClang 15.0.0；Release `-march=armv8 -O3 -DNDEBUG -std=c++17`，ENABLE_NATIVE=OFF，无全局对齐参数、无 LTO/OpenMP。编译记录见 buildinfo/。
- 候选重新独立构建，测试和基准静态 force_load 链接，避免 macOS 工厂注册库被裁掉。
- 三个基线复用先前保留的静态可执行文件，本次全部重新计时，未复用历史性能数值。来源和 SHA256 见 buildinfo/baseline_binaries.json。955 / 7abc / 9819 的原始矩阵 __text、__const、__cstring 地址与内容哈希完全一致，见 baseline_sections.json；两次已有修复的相关生产代码变动为 x86 分支。
- matrix_sweep.cc、adapter_sweep.cc 与分支提交的 toolkit 逐字一致，IVF 基准源码在 955 至 9819 间不变；统一 benchmark_qos.h。matrix/adapter 用线程 CPU 时间，IVF 用 warm search_impl 墙钟时间。
- 每轮各版本各 3 个独立进程，按版本交错、每次重复反转顺序；第二轮反转首轮起始顺序。每进程内部 matrix/adapter 5 次计时取中位数，IVF 7 次取中位数，再取 3 个进程的中位数。共 72 个完整基准进程；与构建及其他基准串行。
- **调度限制：macOS 使用统一 USER_INTERACTIVE QoS + taskpolicy -a，并未硬绑某个核心；不能把它描述成 Linux taskset 的固定核心测量。** 两轮复现、基线代码哈希和单项隔离验证用于控制/解释波动。
- 所有比值为 FINAL / 基线耗时，小于 1 为变快；原始日志、min/max 和中位数均保留。不将分组中位数持平当作所有形状通过。

INT4 Rows≤4 的多列保留旧算法，INT4 2×1 没有两轮共同 >5% 回退。FP32/FP64/INT8/INT16 的本轮矩阵项没有两轮共同 >5% 回退；FP16 仅下述 1×1 微形状。
**修正交接说明的一点预期：**x86-only 的 INT4 record n==1 batch 分支在 macOS 的确未启用，但 ARM64 的记录矩阵仍通过 MakeRawDistanceMatrix(IP) 调用这次修改的单列 INT4 核，所以 RecordL2/IP 32×1 和旧 IVF INT4 record 本次确实变快；不能据“batch 分支 x86-only”推导 macOS record 完全不受影响。INT4 record n>1 则先返回转置+pair fallback，未走新大多列核。
普通 INT4 MIPS 32×32 通过 mips_euclidean_metric.cc 的 raw IP/L2 矩阵，因此承接大多列回退。IVF warm 基准覆盖的是单查询列扫描：本轮 24 项没有 >5% 回退，不能据此掩盖通用 many-to-many / MIPS 32×32 的回退，也不能外推所有 IVF 服务负载。

## 7. 反汇编定位

### INT4 大多列：实际内核变化，非仅噪声

`disasm/{9819,final}_{16x16,32x16,32x32}_{L2,IP}.asm` 覆盖全部 12 项（dim 在运行时传入，相同形状两种维度共用函数）；适配器见 *_adapter_int4_32x32.asm。
- 以 32×16 L2 为例，旧列循环每个向量对/8维读取 1 个打包 query word，再做 8 次查表；新循环先把 query_nibbles 写入栈，再每对做 8 次 query byte 读取 + 8 次查表。额外的 7 次 query load 及展开写入增加访存成本。
- 新版 8 个 table-row 指针在该形状主要保留在通用寄存器中；实际可见问题是展开后的 query 字节数组落栈，不能笼统说“rows[8] 指针全部溢出”。
- 32×16 的列循环静态指令数虽然 38→31，但内存 load 数增加；全函数 105→166 条，栈局部空间 sub sp 2064→2192，直接 [sp] 访问指令 8→26（仅静态统计，不是动态事件数）。32×32 全函数 111→229、直接 [sp] 访问 8→43。
- 因此 x86 上“少位运算”获益不能直接外推到 Apple M3/Clang。两轮一致回退 + load/栈访问证据支持其为新内核结构导致。未采集硬件性能计数器，未把具体端口/缓存瓶颈当作已证明的事实。

### FP16 IP 1×1 d128：整程序布局相关回退

- 完整 sweep 两轮 1.342 / 1.325×9819：约 8.96→12.03 ns 和 8.849→11.729 ns，原始记录保留，未按“噪声”删除。
- warm dispatch 前 31 条指令（重定位地址归一化）一致，调用的 NEON FP16 IP 完整 114 条指令归一化一致；初始化冷路径仅存在链接地址/符号地址差异。见 disasm/unchanged_comparison.json、*_fp16_*.normalized。
- 独立 50ms 采样窗口、各版本 10 进程交错验证：两个可执行文件 __text 地址/长度/SHA256 完全一致；d128 FINAL/9819=1.0126，d512=0.9994。见 results/fp16_focus_summary.json 和 fp16_focus_*.csv。
- 该证据支持整程序布局/调用热点影响，不是 FP16 算术或转置逻辑变化；没有进一步隔离具体指令缓存、分支预测或其他微架构原因。按交接要求，不为此添加对齐参数或改 FP16 内核。完整 sweep 的可复现回退仍是本轮结果的一部分。

## 8. 最小调整建议与两平台结论

建议后续修复仅在 ARM64 的 ComputePackedColumns 中让 Columns≥16 返回旧直接提取循环（原 Rows≤4 继续旧循环）；保留 ARM64 单列查询表行提升、Columns=2/4/8 的新循环以及 x86 全部最终优化。这样直接针对 12 个大多列项及 MIPS 32×32，同时保留已测到的单列/IVF收益。**这只是建议，本轮没有应用或验证这一调整**；实际改动仍需两平台重新跑正确性、兼容和两轮性能，尤其注意小形状布局变化。
Linux x86 的结果来自已校验交接包，并非本机重跑：511 正确性通过、200 fixtures；主要目标回退已解决，adapter/IVF 两轮 0 项 >5%，raw 仍有报告中已归因相同指令流的微形状布局项。
**综合状态：x86 交接结果良好，但本轮 macOS 性能验证未通过。不能宣称两平台无退化；应先调整 ARM64 大多列策略，再决定合入。**
